# Plan 20 — Remove Vector Search (local + cloud embedding, LanceDB)

> **Note (2026-09-30):** `bench-reports/`, the retrieval-only suites (`benchmarks/llm_tasks_*.yaml`), the old benchmark scripts and all pre-2026-09-30 benchmark results were removed; the one benchmark that counts is `benchmarks/dataset/` (`run-sot.sh`, see `CLAUDE.md` "Benchmarking"). File names below that no longer exist are recoverable from git history at commit `5d413ea`. Numbers below were measured on the retired suites: history, not evidence.

*User request, 2026-09-25: fully remove vector search from codegraph — no local
`EmbeddingModel` (ONNX/BGE), no cloud embedding model (Voyage or otherwise), no
vector database (LanceDB) at all. Confirmed explicitly twice after being asked
to clarify scope (cloud-provider choice, and whether a local vector index would
remain): "remove fully the local embedding and also cloud embedding" / "Remove
LanceDB, also if any cloud vector existed => remove also DO NOT USE Vector
search for our codebase."*

## What this reverses, stated plainly

`CLAUDE.md`'s core thesis is currently "fused hybrid retrieval: vector search +
graph expansion + reranking in one pipeline." This plan removes the vector leg
entirely. The retrieval pipeline becomes: **lexical (FTS5/BM25) + graph
expansion + personalized PageRank + rerank** — permanently the code path that
today only runs when the embedder is a stub (`embedding_degraded = true`).

This is not a net-new mode to build — it already exists, is already wired
through the whole pipeline, and is already benchmarked:
`bench-reports/lexical-semantic-vs-no-semantic-2026-08-07.md`,
`bench-reports/lexical-readeditorstate-tiebreak-investigation-2026-08-17.md`,
`bench-reports/keycloak-cross-repo-generalization-2026-08-20.md`. **No-semantic
mode is currently 100% (40/40) on the lexical suite and 34/40 (85%) on
keycloak**, vs. semantic mode's 100%/100%. Removing vector search makes the
85%-on-keycloak number the permanent ceiling for non-lexical-friendly repos —
6 of keycloak's 8 no-semantic misses were diagnosed as having "no textual
bridge in the source at all — unfixable without a model"
(`bench-reports/keycloak-cross-repo-generalization-2026-08-20.md`).

**Correction to an earlier draft of this plan**: the user confirmed the
*removal* explicitly, twice. They did not separately confirm accepting the
85% keycloak ceiling as a permanent state — that number was surfaced by the
assistant, not evaluated by the user in isolation. This plan now treats
closing that gap as in scope via **Phase 8** (an optional cloud-judge rerank
signal, the Jev-style mechanism discussed earlier in this session), not as an
accepted permanent loss. If the user does not want Phase 8, it's a separable,
optional addition — Phases 1-7 (the removal itself) stand on their own either
way.

**Mechanical consequence worth calling out**: because "no vector search" is
already a real, tested code path, this plan is mostly *deletion* — removing
the branch that made the degraded path conditional, not building new retrieval
logic. The risk is in the surface area (crate boundaries, config, CLI, MCP/API
schemas, docs) touched by something that's been part of the architecture since
Plan 04/05, not in the retrieval logic itself.

## Phases (land and test each before the next — do not big-bang this)

1. **Decouple FTS5 indexing from the vector-write path** (`codegraph-watcher/src/worker.rs`, `codegraph-store`, `src/server.rs`). Land this *first*, before deleting anything, so it's independently testable: `flush_embed_batch` and the backfill path stop calling into the embedder/vector store and write FTS5 directly from `Chunk`. At this point `VectorDb`/`EmbeddingAdapter` still exist but nothing live calls them from the watcher. Two things beyond a straight deletion, both read from the current source, not assumed:
   - **The checksum commit is currently gated on the vector write succeeding**, not just chunk-build: `flush_embed_batch` only advances a file's real checksum (off the `0`/pending sentinel that drives retries) *after* `vector.upsert` succeeds, and returns early on vector-write failure without ever calling `upsert_fts_batch`. Once there's no vector write, gate the checksum commit on the FTS5 write succeeding instead — a file whose FTS5 upsert fails must stay at checksum `0` and retry, the same guarantee the vector-write gate provided today.
   - **A real, pre-existing race gets more consequential.** `full_index_graph`'s graph-only pass marks the project `IndexState::Fresh` (`src/server.rs` ~L152, `worker.rs` ~L148) before `embed_backlog` (today: chunk-build + embed + vector/FTS5 write) runs in the background `tokio::join!`. A query landing in that window today gets degraded-but-not-empty results (graph tools work; semantic search is briefly unavailable). Once FTS5 is the *only* content-search channel, that same window means `find_relevant_code`-style queries return nothing at all until the backlog catches up — a harder failure than today's softer degradation. **Decide explicitly, don't default silently**: either (a) fold chunk-build + FTS5 write into the synchronous graph-only pass before marking Fresh — plausible now that there's no ONNX inference cost left to avoid (that was the actual reason Plan 07 split graph-only from embedding, per `checklist.md`'s "~9s" note), but must be re-measured against that ~9s baseline on a real repo before assuming it's still cheap; or (b) keep FTS5 population in the background backlog and accept/document the empty-window race as a known limitation. Pick (a) unless a real measurement shows it regresses Fresh-marking latency unacceptably.
2. **Collapse the retrieval pipeline** (`codegraph-core/src/retrieval/pipeline.rs`, `config.rs`, `types.rs`, `embed.rs`). Drop `VectorStore`, `EmbeddingAdapter`, HyDE, `alpha`, `vec_score`, the `embedding_degraded` branch — inline the lexical+graph path as the only path.
3. **Delete the crates/modules**: `codegraph-embed` (whole crate), `codegraph-store/src/vector_db.rs`, `StoreCoordinator`'s vector field, workspace deps (`ort`, `lancedb`).
4. **CLI/config surface**: remove `--local-embedder`, model-selection prompts, `ensure_model`, `scripts/download-model.sh`, `EmbeddingConfig`, `codegraph status`'s model column.
5. **MCP/API/UI surface**: `watch_status` schema, tool descriptions, REST response shapes, web UI audit.
6. **Docs**: `CLAUDE.md` thesis + invariants + stage-order rewrite, `README.md` rewrite.
7. **Regression benchmark gate**: `scripts/llm-task-eval.py` against both the lexical suite and keycloak. Must land at or above the existing no-semantic baselines (**lexical 40/40, keycloak 34/40**) — those numbers are exactly what this pipeline already produces today under `embedding_degraded`, so anything below them means the removal introduced a real bug, not an expected semantic-mode loss. Update `checklist.md`'s Progress Summary with the confirmed numbers, not assumed ones.
8. **Optional — cloud-judge rerank signal, to close the keycloak gap Phase 7 measures. Built 2026-09-25, user-requested.** Separable from Phases 1-7 as intended — those stood on their own before this landed. What was actually built, vs. what this section originally scoped:
   - Config-gated, `[retrieval.jev] enabled = false` by default — matches the plan.
   - **Fetched TypeSafe AI's real API docs first** (`https://docs.typesafe.ai/api`, not the secondhand LangChain blog-post summary this plan was originally written from) before writing any request/response code, exactly as required below. Real shape: `POST /v1/systemone`, bearer auth, `state`/`model`/`questions` request, `noul`/`choice`/`score` question types, `answers` response map.
   - **Boundary discipline changed from what this section originally proposed**: rather than a new single-purpose crate (`codegraph-jev`) or bolting it into `codegraph-store`, it's a new crate `codegraph-decision-engine` — the `RelevanceJudge` trait lives in `codegraph-core` as planned, but the concrete implementation crate is named and structured to hold *multiple* provider adapters as sibling modules (`jev` is the first), mirroring exactly how the old `codegraph-embed` crate held both `BgeSmallModel` and `VoyageModel` under one `EmbeddingAdapter` trait. User-suggested mid-build, adopted before any other code referenced the old crate name.
   - A new Stage 5 in `RetrievalPipeline::query()` (not inside `rerank()` itself, which stays synchronous and pure) — a per-candidate relevance judgment over the widened top-N pool, added as an additive bonus (`config.jev.weight * relevance`) outside the `beta+gamma≈1.0` budget, same pattern `name_match_bonus` already uses.
   - **Follow-up, same day**: user supplied a real OpenRouter API key for `typesafe/jev-1.13`. Verified working end-to-end against the live API (routed through OpenRouter's schema-compatible `/api/v1/systemone`, zero code changes needed — just `base_url`/`model`/`api_key` config) — `jev_active: true`, real network-latency signature (~850-880ms vs. this project's normal ~2-5ms), zero errors. **Then benchmarked against the Phase 7 baseline, same day, user-requested**: keycloak 33/40 → 36/40, identical across 3 repeated runs (first working config, `top_n=20`).
   - **Second follow-up, same day**: diagnosed the remaining 4 misses directly against raw SQLite FTS5 ranking (bypassing the pipeline) rather than guessing — found `kc-sg-12` alone close enough to reach via recall widening. Tried a Jev-gated `lexical_search` top_k widening (`max(req.top_k, jev.top_n)`, only when Jev active — the *un*gated version of this exact idea was already tried and reverted twice on this corpus in Plan 16), raised `jev.top_n` 20→50. **Regressed**: 36/40 → 34/40, reproduced twice, the targeted task still didn't flip. Reverted the default back to 20.
   - **Third follow-up, same day**: user relayed real-world Jev operational guidance (32K-token context, pay-per-input-token, "keep chunks tight" scoring many candidates at once) that pointed at the actual cause — `apply_jev` was sending every candidate's full, untruncated snippet, so 50 candidates was a much bigger single judging payload than 20. Added snippet truncation (`JEV_CANDIDATE_SNIPPET_CHARS=300`), re-tested `top_n=50`: **36/40 → 38/40, reproduced 3×** — `kc-sg-07`/`kc-sg-08`/`kc-sg-12` all flipped (more than the rank-based diagnosis predicted), `kc-sg-06` (rank ~1279) correctly stayed unreachable. **Also closed the previously-open gap**: ran the lexical-suite regression check with Jev enabled for the first time — 40/40, unaffected, reproduced twice. **Shipped**: `jev.top_n` default raised to 50 for real this time, backed by a measured, reproduced, dual-corpus result. Full arc in `bench-reports/plan20-phase8-jev-keycloak-benchmark-2026-09-25.md`. Not done: individually re-diagnosing `kc-sg-15` (the one new loss traded for 3 gains), and TypeSafe's `"score"` question type as a possibly-better fit than one `"noul"` per candidate.

## Open decisions to resolve during implementation, not guessed here

- **New default `beta`/`gamma`.** Today's degraded-mode renormalization is `beta/(beta+gamma)`, `gamma/(beta+gamma)` off defaults `beta=0.2, gamma=0.1` → effectively `0.667/0.333`. Recommend making that the literal new default rather than re-deriving from scratch, since it's the only empirically-validated point — but confirm against Phase 7's benchmark, don't assume it transfers unchanged now that it's load-bearing for every query instead of a fallback.
- **The direct-hit `graph_credit` damping (0.5×).** It was validated and shipped specifically as an `embedding_degraded`-gated, "mathematical no-op outside that mode" tweak (`checklist.md` Plan 16, 2026-08-18). Once degraded mode is the *only* mode, it stops being a niche gated tie-break and becomes a core scoring term for every direct hit — worth a fresh sweep (e.g. 0.25/0.5/0.75) against Phase 7's benchmark rather than assuming 0.5 is still right once it's always active.
- **`EmbeddedChunk` → new name.** Suggested `IndexedChunk`; pick whatever reads clearly once "embedded" is no longer accurate.
- **Whether `StoreCoordinator` still earns its keep** as a thin wrapper once it's just `graph.upsert_*` with no second phase, or whether callers should just use `GraphDb` directly. Decide once Phase 1/3 show what's actually left in it.
- **Ship gates in `CLAUDE.md`**: "MRR ≥ 0.50 on benchmark suite" and "Binary ≤ 200MB stripped" were both written with a real embedder in mind. Re-measure both post-removal (expect binary to shrink substantially, MRR to be computed against the lexical+graph pipeline) and update the doc with real numbers in Phase 6, not projected ones.
